XuGo 从设计之初就着眼于人与 agent 如何共同探索数学。它的核心理念是，每完成一次证明，都有机会改进引擎、发现和提炼可复用的数学结构，使引擎与定理库共同发展。

这种工作方式包含两个相互促进的循环：

  • 证明过程中暴露出的工具问题，会推动引擎功能和 agent 指令的改进，使后续从全新上下文开始工作的 agent 更有效地完成证明。
  • 跨章节反复出现的推导可以提取为公共引理和数学结构，为后续的证明提供更合适的抽象。

快速编译与重放使这两个循环能够频繁进行。随着定理库不断发展，用来构建它的工具也在持续改进，库中的数学概念与结构则不断得到梳理和完善。

定理库

在 XuGo 中，定理库里的每份证明都是可编译、可运行的 Go 程序。定理库并非静态收录数学成果的百科全书，而是一个不断重构的软件系统。每证明一条定理，库中新增的不仅是一个可以引用的结论，还有一份可以阅读、拆解和重新组织的证明。其中的局部构造与证明实际用到的假设，都可以为后续工作所用。

定理的身份由其陈述决定，而不取决于名称或所在位置。名称、包和文件等组织结构与逻辑层相互独立，因此重新组织定理库并不涉及逻辑上的改动，只需对 Go AST 进行机械重写。这使定理库能够在发展新理论的同时，不断完善已有的基础理论。

卡片图

开发一个新的数学章节时，首先设计其中的数学陈述，再着手证明。人与 agent 通过讨论确定章节的范围、定义形式和成员的编排顺序，然后将每条尚未证明的定理写成一张卡片。在 XuGo 中，卡片不只是一条自然语言的待办注释，也不是普通的占位符，而是一个一等 Go 变量，包含完整的形式化陈述、泛型类型签名和明确的依赖列表。内核使整个定理库都可以引用这张卡片，注册表则记录哪些结果依赖于它。

编译和重放机制直接作用于卡片图。因此，即使尚未完成证明，这些卡片也已经构成一张经过类型检查和依赖关系检查的有向无环图（DAG）。后续章节可以直接引用前面的卡片，不必等待相应的证明完成。定义中的缺陷或接口之间的不一致，可以在编译阶段或独立评审中发现。在卡片阶段，人就可以像审查已证定理一样，审查和调整章节的数学结构。

卡片图确定后，各张卡片的证明工作便可以独立进行。每张卡片都可以分配给不同的 agent，以任意顺序并行证明。卡片为分工提供了稳定的数学接口：即使从全新的上下文开始，agent 也可以根据明确的陈述和依赖关系展开证明，完成后仍保持原有陈述和定理身份不变。一旦卡片的证明完成，引用它的定理便自动获得这份证明，无需改动一行代码。

定理库本身也为制定证明方案提供帮助。XuGo 的注册表记录每条定理的陈述、所用定义、实际依赖的结果以及尚未证明的依赖卡片，并支持查询。面对一个证明目标，agent 可以先查询定理库，了解它依赖哪些结果、哪些已经证明、哪些仍是未证卡片，以及哪些已有定理可以用于当前证明。卡片的说明中也可以记录预期的证明思路。这些信息还便于检查证明的完整性：每个结果都可以列出自己仍然依赖的未证卡片。当这个集合为空时，它所依赖的未证假设就已全部消除。

证明会话

证明的探索过程在内核层面的 prove session 中进行。会话以卡片的证明目标为起点，逐步建立一棵不断分叉的搜索树。Agent 尝试合适的推理步骤，由此产生新的子目标，可以直接解决的叶节点则交给内置的自动处理器。Agent 可以探索不同的推理路径，必要时回溯，也可以将一条分支中发现的中间节点用于另一条分支。

在证明状态树上进行搜索，或在交互式环境中使用自动证明器，都不是 XuGo 首创的。XuGo 的特点在于以下四项设计：

  1. Agent 与引擎之间的交互遵循严格的内核推导规则。每次 probe 都会返回成功或失败的结果，并给出具体原因。需要搜索的反驳推导会被记录下来。探索期间，agent 可以尝试不同路径、回溯并调整论证结构。推导一旦被记录下来，就可以交给其他 agent 阅读、引用和独立验证。即使更换 agent、耗尽上下文窗口或中断会话，已经得到的结果仍然具有明确的身份，并且可以独立验证，后续 agent 可以在此基础上继续工作。多个证明节点可以分别完成和检查，再按照明确的依赖关系组合起来。这大大降低了跨领域、多 agent 协作的难度。
  2. 自动化围绕作者明确写出的中间命题和数学前提展开。每个证明步骤只将指定的事实交给自动处理器，并在本次调用中清除其余假设。因此，证明正文明确记载了每一步结论所依据的事实。Agent 可以集中精力设计论证的数学结构：需要引入哪些中间结论，应当使用哪些已有引理，又有哪些条件需要事先建立。这些选择都明确体现在证明正文中，读者可以据此理解和检查论证。如果某一步失败，agent 只需检查当前的局部命题，例如是否遗漏了隶属条件、是否尚未建立所需的结构，或者所选引理是否足以推出当前结论。
  3. 当探索树的所有叶节点都关闭后，Emitter 根据已记录的推导，按照依赖顺序将中间命题、分支和引用关系导出为 Go 代码。这样，agent 可以直接核对每个节点究竟证明了什么，无须从对话和 tactic 调用历史中重新梳理论证。即使主要证明尚未完成，已经证明的辅助结论也可以先写入章节，供后续证明使用。导出后，agent 会根据中间结论和分支的数学含义为它们命名，遵循章节已有的记号和引用规范，将零散步骤整理成连贯的论证，并判断哪些局部结果值得提取为公共引理。如果有了新的证明思路，agent 可以回到 session 中继续探索，也可以直接通过自己擅长的 Go 程序重构来实现。
  4. 证明整理完成后，由独立的评审者重新检查其可读性：一位不熟悉这条定理的数学家，能否仅凭证明脚本理解论证思路？删去所有注释后，关键推理是否仍然清楚？评审者逐一检查各个数学节点的作用，寻找重复论证、隐含的上下文依赖以及未使用的条件。最终形成的证明脚本既保留了 session 中已经验证的数学内容，也将其整理成便于阅读、引用和进一步重构的完整论证。

第一个循环：通过证明不断改进工具

在这个循环中，每个负责证明卡片的 sub-agent 都从全新的上下文开始工作，并重新阅读指令文件。经验不依赖单个 agent 的记忆，而是通过引擎代码和指令文件的改进积累下来。Agent 在 session 中遇到困难时，会与人共同讨论解决办法，并据此增加引擎功能、提供更准确的诊断或开发新的抽象工具。

以 ByElementarity 为例。实闭域和代数闭域上的四个定理——Ax–Grothendieck、多项式方程组的下降、字典序极小点的存在和多项式 Brouwer——原先都需要在证明中分别构造一阶公式、证明公式的闭性，并给出求值桥接，总共涉及四十个子命题。Agent 将这套重复的推导过程封装为一个步骤：先将定理陈述反射为一阶公式，再通过名称引用一系列引理，包括 first_order 中的量词桥接引理、polynomial_encoding 中的编码桥接引理，以及各个公式章节中的求值引理，以内核推导的方式完成模型论上的迁移。这个 tactic 实现后，原来的子命题以及不再被引用的成员都被删除，而四条定理的陈述与已证状态保持不变。这正是 LCF 的优势：tactic 的能力来自库中已经证明的定理，其可靠性由内核自动保证。定理库每增加一条这样的桥接引理，引擎的能力就得到进一步扩展。

这个循环能够持续进行，依赖一条严格的原则：引擎的缺陷必须在源头解决，不允许在证明文件中绕开这些缺陷。大模型很擅长寻找变通办法。如果允许 agent 通过繁琐的局部证明绕开工具的不足，它就会选择最省力的办法，证明文件也会越来越复杂，而引擎能力却没有得到改善。禁止这种做法，才能让单个证明中遇到的问题推动公共工具的改进，使这一循环持续进行。

第二个循环：数学抽象与程序抽象的统一

在 XuGo 中，对程序进行抽象的过程，也是发现数学抽象的一种途径。软件工程中的 Don't repeat yourself（DRY）原则，与数学中提取公共定理和结构的过程直接对应。对 agent 而言，凭空发现一种深刻的数学抽象并不容易，但识别代码中的重复模式、提取公共部分并进行重构，却恰好是它擅长的事情。

典型的 Lean tactic 脚本由一系列隐式改变证明状态的指令组成，执行 rw 或 simp 后的目标并不写在源代码中。作者虽然可以用 have 为中间结论命名，但并没有义务这样做。自动化工具可以使用整个上下文，因此脚本也没有明确记载每一步实际使用了哪些前提。两个数学上同构的推导，在源代码中可能呈现出完全不同的形式，agent 很难仅通过阅读代码发现它们共有的数学结构。XuGo 要求证明脚本本身能够呈现连贯的数学论证，自动处理器也只能使用明确列出的前提。这样，反复出现的数学论证就更容易在代码中表现为重复的结构，agent 可以通过后文所述的重构机制识别并提取它们。可以自动检查的要求由 lint 保证，独立评审则负责判断自动化工具无法判断的问题：不了解证明过程的读者，能否仅凭代码理解整个论证？

由于证明本身就是 Go 程序，日常开发可以直接利用 Go 生态中已有的工具。Agent 会在不同章节和数学领域之间寻找反复出现的模式、概念和相似的证明方法。例如，不同章节中的证明可能分别验证商映射在选取陪集代表元时的良定义性；数域与代数曲线中的维数计算，也可能采用一系列同构的代换步骤。发现这些重复模式后，agent 会提出可能的数学抽象，与人共同讨论：反复出现的论证背后，是否存在一个尚未被命名的代数或几何结构？如果存在，应该将相应的定义或定理放在哪个章节？

这种重构的效果可以从四个方面检验：

  • 依赖范围：每条定理都记录了证明实际使用的依赖，重构后这些依赖的数量是否减少？
  • 证明简化：原先在不同领域中反复出现、每次都需要十几行 Have 步骤的局部推导，是否已经分别简化为一行 cite？
  • 可读性：将陪集、坐标等底层细节封装在具名的数学概念中后，上层定理的证明是否更加简洁易读？
  • 结构复用：注册表中的跨领域复用比例是否提高，传递依赖的范围是否缩小？

然而，要让这种重构成为日常工作的一部分，还必须满足一个现实条件：重构足够快。当 agent 将一条公共引理提取到基础章节，并更新十来处使用它的证明时，编译和重放必须能够立即提供反馈。在 mathlib 中，修改一个底层代数文件，依赖它的所有文件都需要重新编译，一次检查可能耗时几十分钟到几个小时。因此，底层重构需要经历耗时的 CI 流程和人工评审，难以成为 agent 的常规操作。在 XuGo 中，Go 代码的编译时间以秒计算，重放一个章节以及直接依赖它的其他章节，只需几秒到一两分钟。即使修改了最底层的基础理论，在多核 CPU 上重放整个定理库也只需十分钟左右。这样，提取一条引理、更新十处证明、运行一次 replay，就可以成为 agent 的常规操作。

这样的速度得益于 Go 自身的编译效率、不涉及 Typeclass 搜索和 Elaboration 开销的轻量 LCF 内核，以及模块化验证。重放一条定理时，对其他已注册定理的验证以其陈述为界，无须在每次引用时重新展开共同的基础证明。

共享章节越精简，重放就越高效；重放越高效，agent 就越容易频繁重构，从而进一步精简共享章节。在这一循环中，每完成一个重要定理，都有机会进一步完善它所依赖的基础章节。为解决当前问题而提取的引理会归入更基础的章节，原先需要这些引理的证明则改为直接引用，使各章节能够专注于自身特有的数学内容。例如，沿着依赖关系追溯，数域类群的有限性与椭圆曲线上的 Riemann–Roch 定理，都依赖同一套关于可逆分式理想、模与维数、域与多项式的基础理论。整数格、分式理想和作为向量空间的域扩张，也都引用同一套模的定理。公共论证在库中只保留一份，并被越来越多的数学领域复用；每个重要定理则只需保留自身特有的对象和核心论证。

去重即泛化

并非代码中每一种重复模式都对应着一个新的数学概念。某种反复出现的模式可能已经有相应的常量，只是此前没有被注意到；仅仅根据代码结构进行归类，也可能得到不符合数学直觉的抽象。

因此，agent 负责提出抽象方案，replay 验证其数学上的正确性，独立评审和人的判断则负责衡量这些抽象的数学意义与审美价值。宪章中的约束与评审过程中的去重机制相互配合：agent 在宪章的约束下精简每条定理的假设，保留证明真正需要的条件；内核检查这些条件是否足以完成证明；评审则识别反复出现的论证，并确定它们适合归入哪个章节。由此形成一个持续完善定理库的反馈循环。

以理想分解为例，代码将 Dedekind 整环定义中的各项条件拆开，分别考察证明的每一步实际需要哪些性质。对于一个域的子环，只要每个非零理想都有有限指数，且该子环在该域中整闭，就能推出非零极大理想可逆。理想分解的核心定理 IdealFactorizationExists 所需的条件还要更弱：只要求给定的非零理想之上的严格递增理想链长度有界，以及包含它的极大理想可逆。每除去一个极大理想，剩下的理想就严格变大，因此链长的上界保证这一过程终止。唯一性的证明则只需要参与分解的极大理想可逆，以便消去公共因子。

Riemann–Roch 的例子也体现了这种思路。在定理库采用的曲线模型中，serre_duality.RiemannRoch 只要求曲线数据和一个可逆的格对（lattice pair），曲线可以有奇点。光滑性不再是整个定理的共同前提，而只在恢复经典表述时才需要引入。重构由此揭示，定理的核心适用于更广泛的对象，而经典结论只是其中的一个特例。

在证明代数性的传递性时，agent 需要用到有限多个代数元生成有限扩张这一事实，却发现同样的论证已经存在于 galois_correspondence.SeparableRootFieldGalois 的局部证明中。将这段论证提取为 algebraic_element.FiniteAlgebraicAdjoin 后，新证明有了所需的公共引理，原证明中两次使用这段论证的地方也改为直接引用。这一过程既简化了新的证明，也改善了原有章节。新的证明任务揭示了一段已有论证的独立价值，使它成为具名的公共引理，并被放入合适的章节。此后，所有使用它的证明都引用同一份经过验证的结果。定理库中尚未被单独命名的局部推导，也因此成为不断发现新数学抽象的来源。

XuGo 的依赖图明确记录了定理之间的依赖关系，内核也知道每条定理的证明实际使用了哪些谓词。在此基础上，agent 可以不断调整定理的陈述，使每条定理只依赖其证明真正需要的假设，而不必沿用传统表述中预先组合好的条件。当同一套论证被不同数学领域反复使用时，这一过程便能系统地揭示尚未被命名的推广和可能的数学结构，其中一些或许比传统定义更加自然、更接近问题的本质。教科书中的数学定义常常将多项性质组合在一起，以适应人类工作记忆的限制。而 XuGo 的显式依赖图使我们能够分别考察这些性质在证明中的作用，根据实际的逻辑依赖重新组织数学概念。新的数学，或许正是在这一过程中产生的。
